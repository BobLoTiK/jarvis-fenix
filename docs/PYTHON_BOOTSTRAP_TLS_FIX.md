# Исправление загрузки Python в чистой Windows

Этот этап включён в общий пакет с выбором модели Ollama. Для последнего общего
архива см. BOOTSTRAP_PYTHON_OLLAMA_UPDATE.md; Python-архив отдельно не требуется.

## Что доказано и что ещё не доказано

В пользовательском логе Windows Sandbox загрузка Python через urllib встроенного
лаунчера сначала завершилась ошибкой DNS, затем CERTIFICATE_VERIFY_FAILED
(unable to get local issuer certificate). В той же сессии Invoke-WebRequest
скачал официальный Python 3.11.9 x64, а Get-AuthenticodeSignature вернул Valid,
издатель Python Software Foundation. Точная причина различия доверия OpenSSL
лаунчера и Windows не установлена. Ошибка относится к подготовке Python,
не доказывает неисправность основного GUI или причину прежнего сбоя ярлыка.

## Что изменено

- Только Python-bootstrap использует системный Windows PowerShell 5.1:
  HTTPS/TLS 1.2, фиксированный официальный URL python.org, редиректы запрещены.
- Не отключаются сертификаты, не добавляются корневые сертификаты, не меняются
  настройки Windows, не добавляются Python-зависимости. Профили PowerShell не
  загружаются; shell=True и обход ExecutionPolicy не используются.
- Перед публикацией EXE требуется Authenticode Status=Valid и имя подписанта
  Python Software Foundation. Подпись проверяется ещё раз перед запуском.
- Непроверенный или повреждённый EXE не запускается. Старый EXE из общего TEMP
  больше не считается готовым установщиком только по факту наличия файла.
- У каждой попытки своя временная папка phoenix-python-*. Загрузка идёт в
  .part.exe, затем переименование. Известные временные файлы удаляются при
  ошибке и после завершения запуска установщика. Нет рекурсивного удаления.
- Нативная загрузка не сообщает точный байтовый прогресс: индикатор ожидания,
  затем завершение после проверки; проценты не выдумываются.
- Таймаут внешнего процесса загрузки/проверки 240 с; повторной проверки 60 с.
  При недоступном PowerShell, сети или подписи — отказ, понятное сообщение и лог,
  а не запуск без проверки. Политики управляемой Windows не обходятся.
- Команды создания venv, pip, установки Python и запуска приложения сохранены.
  Это не readiness-патч, не оптимизация TTS и не исправление Диалога.
- Vosk/pip и другие загрузки этим патчем не переведены на новый транспорт.
  Их работоспособность — следующий этап Windows-приёмки, не объявленный успех.

## Применение — прямо в корень jarvis

1. Закрыть Феникса. Сохранить копии заменяемых исходников/документов.
2. Содержимое ZIP скопировать в C:\jarvis (там находятся launcher.py и папка
   jarvis). Объединить scripts, tests, docs и .github; заменить одноимённые файлы.
   В архиве нет обёртки jarvis и нет личных конфигов, профилей, моделей или venv.
3. На Windows в существующей .venv311:

```powershell
.\.venv311\Scripts\python.exe -m pytest tests/test_launcher_download.py tests/test_launcher_ui.py tests/test_build_setup.py tests/test_release_payload.py -q
.\.venv311\Scripts\python.exe snapshot.py --check
.\.venv311\Scripts\python.exe scripts/build_setup.py --check
```

**Важно: старый Феникс.exe содержит старый launcher.py внутри PyInstaller.**
Замена .py рядом с ним не исправляет уже собранный EXE. Нужна новая сборка:

- Как раньше через GitHub: отправить изменённые исходники в свой репозиторий,
  Actions → build-release → Run workflow, затем скачать свежий Artifacts.
  Ручной запуск не создаёт публичный Release. Старый v2.1.0 не переставлять;
  для публичного исправления выбрать новую patch-версию.
- Либо локально на Windows с build dependencies и Inno Setup 6:

```powershell
.\.venv311\Scripts\python.exe scripts/build_setup.py
```

Этот архив содержит исходники, а не пересобранные Windows EXE/Setup.

## Приёмка в Windows Sandbox

1. Сначала сохранить наружу нужные логи старой сессии; после закрытия Sandbox
   они исчезнут. Открыть новую чистую песочницу.
2. Перенести только НОВЫЙ Феникс_Setup.exe. Не переносить проект, Python или venv.
3. Проверить скачивание Python, сообщение о проверенной подписи в
   C:\ProgramData\Phoenix\logs\launcher.log и открытие официального installer.
4. Завершить установку Python; проверить дальнейшие этапы venv/pip/Vosk/GUI.
5. Проверить полный выход и повторный запуск. Если следующий этап упадёт,
   сохранить новый журнал, не объявлять всю установку исправленной.

Опциональная проверка реальной Windows-загрузки из исходников, без установки:

```powershell
$env:PHOENIX_TEST_PYTHON_DOWNLOAD = '1'
.\.venv311\Scripts\python.exe -m pytest tests/test_launcher_download.py -q
Remove-Item Env:PHOENIX_TEST_PYTHON_DOWNLOAD
```

Она скачивает около 25 МБ, проверяет подпись и удаляет тестовый файл. Проверка
из исходников не заменяет проверку нового собранного EXE в чистой песочнице.

## Проверено при подготовке патча

Linux, Python 3.13: 75 passed, 2 skipped в четырёх файлах bootstrap/build tests.
Сеть, подписи и процессы Windows в переносимых тестах подменены. Пропущены
реальный Windows PowerShell с неподписанным EXE и opt-in скачивание в Windows.
В release workflow добавлен запуск этих регрессий на Windows до сборки;
там неподписанный EXE проверяется настоящим PowerShell, live download остаётся opt-in.
Windows EXE/Setup здесь не собирались. Результат новой чистой установки неизвестен.
