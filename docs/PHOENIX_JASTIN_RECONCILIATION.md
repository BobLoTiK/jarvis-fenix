# JASTIN — целевое видение Феникса: план перехода

JASTIN — целевой план реализации Феникса и видение работодателя.
Цель — максимально реализовать это видение с обоснованными оговорками.
Документ сопоставляет исходные требования с кодом и задаёт маршрут перехода.

**Статус:** план перехода, не выполненная миграция. Ни код, ни зависимости,
ни пользовательские данные этим согласованием не изменены.
Очередь — [PLAN](../PLAN.md), ближайший шаг — [NEXT_STEPS](NEXT_STEPS.md).

Целевое видение задаёт направление. Различия текущего кода и S1/S2 —
**разрыв до целевого состояния**, а не основание отменять требования.
Если источники расходятся, вопрос фиксируется на согласование с пользователем/
работодателем. До ответа сохраняем рабочее поведение; не выдаём самостоятельно
выбранную замену за утверждённое требование. S3 не переименовываем в готовый
Phoenix SDK и не обещаем запуск Uvoxus-плагинов без совместимого контракта.

Метки: **есть** — подтверждено исходниками; **частично** — есть основа;
**целевой этап** — включено в маршрут; **уточнить** — требуется решение;
**проверить** — требуется замер/целевая приёмка. Отложенная по зависимостям
задача остаётся частью цели, а не автоматически исключённым бэклогом.
Чужие отметки готовности, лицензии и оценки ресурсов не заменяют нашу проверку.

## 2. Текущее → целевое → путь перехода

| Подсистема | Что есть сейчас | Цель JASTIN / предоставленных планов | Путь и статус |
|---|---|---|---|
| Оркестрация | Потоки, command pipeline, блокировки, stop-token | Отдельный voice_core, модульный оркестратор, Event Bus | Общий контекст/события → протокол → вынос границ в процессы; ZeroMQ — целевой кандидат, не готовый transport |
| STT/VAD/wake | Silero VAD, Vosk с quality gate, опциональный faster-whisper | Sherpa-onnx/GigaAM, Vosk wake/fallback | Адаптер и общий корпус; Vosk сохраняется как минимум wake/fallback. Миграция основного ASR после сравнения и согласования, не удаление рабочего пути сейчас |
| Intent | Fast rules, морфология, typed stages, локальная LLM | fastText, семантика и consensus | Единый набор команд/признаков, offline обучение и версионирование; быстрые правила и проверки не обходятся |
| Личность | Выбираемый профиль, без speaker verification | ECAPA-TDNN, образцы профиля/команд, четыре проверки | Enrollment с согласием, независимая оценка, shadow mode → контролируемое применение; обязательность/ошибки согласовать |
| Права | Текущие confirmation/password gates | Trust L0–L4, многоступенчатые опасные операции | Формальная политика, scoped подтверждения и аудит; проверка эффекта и host-enforced минимум риска |
| Аудио/TTS | Silero → Piper → SAPI, общий PCM, optional AEC3 | Общий голосовой слой, локальные Chatterbox/Qwen3-TTS, варианты cloud TTS | Сначала принять AEC/отмену и bounded streaming; новые движки через интерфейс, с лицензиями/пакетами и замерами |
| Память | JSON профиля/диалога/индекса, Ollama embeddings | SQLite + SQLCipher, DPAPI, общие embeddings | Контракт хранилища → схема/backup → атомарная миграция → шифрование и recovery; сравнить all-MiniLM с текущей моделью |
| Skills | Встроенные handlers и статические custom-команды | Независимые skills/plugins, Python subprocess, жизненный цикл | Capability SDK и внутренний пилот → изоляция/права → внешние плагины; не второй command pipeline |
| Сценарии/макросы | Редактор 1–6 типизированных шагов, ограниченная UIA | Визуальный граф, Litegraph.js, keyboard/mouse/OCR | Схема и executor → безопасный import/export → редактор графа → расширенные действия с проверкой цели |

## 3. Десять предложений интеграции S1 — как реализовать цель

| № | Предложение | Место в маршруте | Оговорка / решение на согласование |
|---|---|---|---|
| 1 | Четыре проверки голоса/команды/фразы/семантики | R3: раздельные результаты и orchestrator consensus | Реализовать структуру проверок, но не считать их статистически независимыми. Проверить на корпусе; «×2» не доказано |
| 2 | Trust L0–L4 | R2 → R3: политика и подтверждения | Уровни и UX согласовать; риск эффекта задаёт нижнюю границу, которую плагин не понижает |
| 3 | Mode E / Exterminatus | R3: отдельное высокорисковое требование | Не вычёркиваем из цели. Уточнить конкретный перечень операций и полномочия; прототип сначала dry-run, затем отдельное разрешение на реальные эффекты |
| 4 | Heartbeat, busy/idle, FIFO | R1 → R2: состояния, ограниченная очередь и контроль живости | Согласовать TTL/отмену/подтверждение отложенных действий; Stop приоритетен. Не запускать устаревшие команды молча |
| 5 | UUID, асинхронные проверки, deadline | R1: request/utterance/response context; R3: checks | Бюджеты измеряются. Для обязательного check таймаут — повтор/отказ, не автоматическое исключение проверки |
| 6 | STT fallback | R2: адаптеры и сравнение целевого ASR | Vosk wake/fallback сохраняется; отказ движка не разрешает низкоуверенный текст |
| 7 | Динамические пороги в шуме | R3: калибровка confidence по условиям | Порог качества и порог авторизации различать; автоматическое ослабление биометрии для опасных действий требует пересмотра и согласования безопасной альтернативы |
| 8 | SQLCipher + DPAPI | R4: целевое хранилище | Нужны миграция JSON, ключи, backup, recovery и охват журналов/индексов; не просто установка библиотеки |
| 9 | Lazy loading/pool/unload | R1 baseline → R2/R5 менеджер ресурсов | Ёмкости/TTL по замерам и бюджету целевого ПК; отсутствие вечных zombie processes |
| 10 | Аугментация голоса | R0/R2 ASR-корпус; R3 биометрия | Согласие и независимый holdout, replay/spoof; аугментации одной записи не заменяют независимые примеры |

Значения 0,5 с / три команды / 500 мс / пять минут — параметры проектирования
из S1/S2, не доказанные оптимумы. Сохранить как кандидаты и проверить.
Фиксированные сроки из документа — исходные оценки, не обещание с нашей стороны.

## 4. Маршрут реализации: от текущего к видению

### R0. Рабочая исходная точка и аудио

Принять последнюю подготовленную сборку, когда пользователь вернётся к проверкам.
Предыдущие Windows-пробы улучшили AEC, но самоперебивания остались. «Х» в «их» —
гипотеза для воспроизведения, не доказанная фонемная причина; удар микрофона
проверять отдельно. Последний пакет no-WinRT/диагностики пользователь не проверял.
Обычный AEC пока Piper, ручная PCM-диагностика Piper/Silero; SAPI — метаданные.
[Диагностика](AEC_LOCAL_DIAGNOSTICS.md), [границы AEC](AEC_PIPER_PROTOTYPE.md).
Setup-приёмка остаётся отложенной пользователем, но обязательной перед релизом.

**Выход:** воспроизводимые сценарии, честный baseline, отмена/начало фразы,
различение echo-only/double-talk. Synthetic тест не заменяет колонки Windows.

### R1. Измеримость, состояние и плавная потоковая озвучка

Общий контекст операции: идентификаторы, профиль, timestamps, deadline и отмена.
Сначала в существующих владельцах, затем как часть межмодульного протокола.
Состояния/результаты: «принято», «в очереди», «выполнено», «отменено»,
«результат неизвестен». Поздний ответ старой операции не меняет новую.
Baseline cold/warm, median/p95; bounded TTS с реальным перекрытием LLM/синтеза/
воспроизведения, порядком, backpressure и немедленной отменой очереди.
Плавная остановка — подраздел ниже; она не лечит ложный barge-in.

### R2. Модульное ядро и первая вертикаль skill

Сформировать typed contracts audio/STT/intent/TTS/storage/skill; сохранить единый
путь safety/confirmation. Ввести версионированный протокол событий, correlation,
ошибки, deadline, backpressure, heartbeat и recovery. Внутренний readonly skill
— проверка контракта, а не конечная замена требуемой системы внешних плагинов.
Затем subprocess pilot и следующий независимый skill через те же границы.
Определить, что выносится в voice_core и когда нужен ZeroMQ; не держать две
конкурирующие системы исполнения. Измерить потерю сообщений/повтор/падение.
В эту фазу — общий корпус и A/B Sherpa/GigaAM, Vosk fallback, fastText/семантика.
Обсуждение кандидатов разрешено; немедленная замена ASR не подразумевается.

### R3. Consensus, голосовые профили и Trust

Enrollment профиля/команд, consent/delete/retention, ECAPA adapter, раздельные
checks и shadow mode, калибровка FAR/FRR, шум/replay/spoof. Четыре канала
реализуются как целевая логика, а не необоснованная формула надёжности.
Trust L0–L4 и многоступенчатые подтверждения связывать с действием/аргументами,
профилем и TTL. Уточнить реакцию при отсутствующем профиле/зависшей проверке.
Mode E не теряем: сначала согласовать операции, UX, полномочия и dry-run;
никаких реальных разрушительных операций как побочного эффекта миграции.
Парольный модуль сейчас SHA-256; отдельная соль/KDF/миграция нужны до заявления
о современном защищённом хранении. Биометрия не единственный фактор опасного доступа.

### R4. Память, управляемое обучение и защищённые данные

Сохранить факты/историю/коррекции. Storage interface, версия схемы, тест миграции
JSON → SQLite, backup/проверка/атомарное переключение и откат, затем SQLCipher/
DPAPI. Задать модель угроз, судьбу embeddings/логов/временных файлов и ключей;
recovery после переустановки не обещать без отдельного механизма.
Общие embeddings для команд и памяти оценить на реальных задачах; не обнулять
знания при смене LLM/модели. FastText обучается на подтверждённых данных,
есть holdout/version/rollback. Подтверждение/просмотр/удаление выученного —
обязательная часть, а не бесконтрольное автосохранение распознаваний.

### R5. SDK, макросы, сценарии, UI и модельные провайдеры

Довести внешний SDK с lifecycle/capabilities, crash isolation и правилами
доверия; typed data-only import/export команд — отдельный от загрузки кода путь.
Граф сценариев и executor сначала со схемой, валидацией и dry-run; затем
Litegraph/визуальный UI. OCR/keyboard/mouse требуют проверки окна/цели/DPI,
ограничений и остановки при неоднозначности; не кликаем вслепую.

Параллельность этих подэтапов определяется ресурсами, не «всё сразу»:

- GUI/dock: vertical prototype PyWebView, сравнение с текущим Flet; выбрать один
  целевой стек при конфликте PyWebView/Tauri, сохранить UX/настройки/отмену.
- LLM router: Ollama как рабочий локальный provider плюс целевой multi-provider
  путь; явное согласие на сеть, secrets, timeout/failover/cost/retention.
- Целевые локальные/облачные TTS: Chatterbox/Qwen3-TTS и варианты из S2 после
  проверки API/весов/лицензий/ресурсов; общий PCM/AEC и отмена обязательны.
- Менеджер модулей/ресурсов и пакетов: совместимость, обновление, отзыв/откат;
  магазин и распространение после этих механизмов, не вместо них.

Это целевые работы JASTIN, а не отвергнутые «чужие расширения». Внешние идеи,
не требуемые видением (например отдельный Hermes/MCP/Telegram-мост), не добавлять
автоматически: при появлении требования определить место в том же маршруте.

### R6. Поставка и целевая приёмка

Чистая Windows, установка/обновление/удаление модулей, отказ сети/модели/голоса,
crash recovery, профили и миграции, DPI/dock, память/CPU и сквозная задержка.
Проверить лицензии конкретных версий кода, голосов, весов и компонентов.
Не добавлять исключения антивируса; подпись полезна, но не гарантия отсутствия
ложных детектов. Два корня путей сохраняются до отдельного решения о portable.
Nuitka — кандидат A/B standalone после стабилизации: сейчас PyInstaller
собирает launcher, ядро — venv. Не обещать ускорения ML от компиляции launcher.

R0–R6 — рекомендуемый порядок зависимостей, не утверждённый работодателем
календарь. Завершение функций отмечать отдельно от целевой Windows-приёмки.

## 5. SDK из Uvoxus: максимальное использование образца с явными границами

Берём подробность S3 за образец будущей спецификации, а не ограничиваемся
«когда-нибудь readonly API». Согласовать, нужна ли бинарная/исходная
совместимость или эквивалентные возможности с нашим API.

- Версия manifest/API, lifecycle register/start/stop, объявленные thread contexts;
  register без тяжёлой работы. Cleanup подписок/таймеров/окон/hotkeys/workers.
- Типизированные capabilities, настройки по plugin + profile, атомарное сохранение,
  отдельное хранилище secrets; доступ через host policy и текущую safety chain.
- Bounded async tasks, deadline/cancellation/correlation, документированные ошибки
  и None/отмена, идемпотентность там, где возможна; timeout не равен rollback.
- Один владелец микрофона, временное право голосового ввода с TTL, резерв Stop,
  release при crash/profile change. Нельзя перехватывать аварийную отмену.
- UI через владельца GUI, без прямого доступа из чужих потоков; настройки,
  события, голос, команды и необходимые модели — через описанные адаптеры.
- Subprocess даёт изоляцию падений, не OS sandbox. AST/Bandit/import blacklist
  не доказывают безопасность; определить доверие к Python-коду и реальный
  механизм ограничения прав. Не исполнять untrusted pickle/архив автоматически.
- Readonly pilot → разрешённые эффекты → внешняя поставка. Для каждой capability
  описать права, потоки, отмену, ошибки и тесты. Не изобретать отсутствующие
  методы `api.*` под видом уже совместимого SDK.

## 6. Небольшие оговорки и открытые решения работодателю

Это не список самовольных отказов от цели. Изменение продуктового требования
требует согласования; техническая оговорка должна иметь причину и альтернативу.

| Вопрос | Почему нужно уточнение | Предлагаемая безопасная трактовка |
|---|---|---|
| Какой frontend обязателен: PyWebView или Tauri/React? | S1/S2 расходятся | Выбрать один по прототипу; Flet пока поддерживаем, миграцию не запрещаем |
| Vosk vs другой wake/основной ASR | Ранее Vosk сохраняли, в S1/S2 разные маршруты | В S2 Vosk wake/fallback сохраняется; Sherpa/GigaAM сравнить как основной |
| LiteLLM / другой router, облачные провайдеры | Разные конкретные реализации в документах | Согласовать provider contract и поддерживаемый список, явный opt-in |
| Четыре проверки и шумовые пороги | Зависимые признаки; риск ложного допуска | Реализовать каналы, измерить и не снижать обязательную защиту при шуме |
| Mode E и минимальные подтверждения | Неясны операции и допустимый ущерб | Уточнить scope, полномочия и dry-run до реального исполнения |
| DPAPI/recovery/portable | Переносимость ключей и пути конфликтуют | Утвердить модель восстановления и безопасную миграцию |
| Требуется ли точная совместимость Uvoxus API? | Это ещё не реализованный Phoenix API | Зафиксировать список возможностей и степень совместимости |
| Целевой минимальный ПК и порядок must-have | Нельзя гарантировать ресурсные цифры из текста | С работодателем выделить обязательный вертикальный срез и бюджеты |

Необязательно отвечать на всё до следующего аудиошага. Но до спорной миграции
решение должно быть принято, а не заменено догадкой помощника.

## 7. Дополнение UX: плавная остановка (остаётся в целевом аудиоконтракте)

### Дополнение из присланного совета: плавная остановка речи

**Принять как требование к будущему PCM-плееру, с поправками. Код не изменён.**
Текущий `jarvis/audio_output.py` пишет PCM через blocking `OutputStream.write`
блоками примерно по 50 мс, проверяет token между блоками и передаёт те же блоки
в AEC tap после микширования. Явного fade-out в этом пути сейчас нет.
Псевдокод с callback не является прямым патчем к нашей реализации.

- При подтверждённом barge-in сразу отменить жизненный цикл старого ответа и
  очистить непроговорённую очередь. Поздние результаты LLM/TTS отбросить;
  новый ввод продолжает приниматься. Fade — ограниченный хвост проигрывания,
  а не отсрочка отмены или повод дождаться окончания слова.
- Плавно свести к нулю **ближайшие ещё не отправленные** сэмплы активного
  проигрывания. Уже переданный драйверу звук назад не изменить. Не проигрывать
  очередь накопленных фраз и не ждать 250 мс накопления ради fade.
- Огибающая непрерывна между блоками и каналами, начинается от текущего gain
  и заканчивается нулём. Линейная или косинусная — сравнить по щелчкам и задержке.
  Нужны счётчик оставшихся сэмплов и состояние операции, а не новый np.linspace
  с gain=1 на каждом callback. Частота/каналы/короткий остаток учитываются.
- 200–300 мс из совета **не фиксировать как обязательный default**: это слышимая
  добавка к задержке barge-in. Выбрать минимальный достаточный de-click хвост
  по измерениям на Windows с учётом VAD, очереди драйвера и реального звука.
  Мягкая остановка не гарантирует завершения фонемы/слова и не лечит ложный trigger.
- Порядок единого PCM-пути: микширование/ограничение уровня → stop-envelope →
  **один итоговый блок одновременно для output и AEC reference**. Не строить
  отдельную независимо вычисляемую огибающую reference. Окончание reference и
  capture/echo-tail согласовать с реально выданным хвостом; не сбрасывать AEC
  раньше него. Это согласование цифрового reference, не обещание точного DAC timing.
- Stop/shutdown не должен ждать длинного мягкого хвоста; предусмотреть жёсткую
  аварийную отмену. Повторный Stop не перезапускает fade и не продлевает хвост.
  Таймаут/ошибка/неподдерживаемый backend — ограниченное завершение без зависания.
- Не вызывать блокирующий stream.stop/close и не делать тяжёлые операции внутри
  realtime callback. Если выберем callback-плеер, его callback только выдаёт
  подготовленный PCM/сигнал завершения; жизненным циклом управляет владелец плеера.
- Контроль PCM возможен у Piper/Silero через общий путь. SAPI/winsound не считать
  поддерживающими такой же fade/reference без отдельной реализации; текущая
  безопасная отмена остаётся fallback, поддержку показывать честно.

**Приёмка:** непрерывность/монотонность огибающей, границы блоков, mono/stereo,
разные sample rate и короткий остаток; точное совпадение итоговых PCM-блоков
output/reference в тестовом tap; отмена очереди/позднего синтеза, повторный Stop,
новый ответ во время завершения старого, ошибка backend. На Windows измерить
trigger → прекращение слышимой речи (median/p95), щелчки и AEC echo-only/double-talk;
нет потери начала пользовательской фразы, наложения и зависания при выходе.


## 8. Контроль прогресса

По каждой целевой функции: требование → существующая основа → контракт →
вертикальная реализация → тесты → Windows-приёмка → статус. Нельзя заменить
функцию документацией/заглушкой или объявить отложенную цель ненужной только
потому, что её пока нет в коде. Нельзя и объявить миграцию готовой по одному
unit-тесту. Изменения целей — с согласованием пользователя/работодателя.

Итог этого шага — исправленная дорожная карта к JASTIN. SDK, биометрия,
SQLCipher, Sherpa/GigaAM, новый GUI, provider router и новая сборка пока не реализованы.
