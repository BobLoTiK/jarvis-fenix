# План реализации Феникса → JASTIN

## Цель

JASTIN — целевое продуктовое/архитектурное видение работодателя.
Стремимся реализовать его максимально, с небольшими обоснованными оговорками.
Нынешний стек — исходная точка, а не основание отменять требования.
Сроки и обязательный первый срез согласуются, не выдумываются.

## Порядок реализации

| Этап | Результат | Приёмка / зависимость |
|---|---|---|
| R0 — стабильная аудиобаза | Диагностика AEC, качество распознавания, начало фразы, Stop, честный fallback | Последний пакет ещё не принят пользователем; реальное Windows echo-only/double-talk; Setup отложен, но релизный gate сохраняется |
| R1 — измеримость и речь | Request/utterance/response context, реальные состояния/отмена, bounded streaming TTS и короткая de-click огибающая | Baseline/median/p95, речь до конца LLM-ответа, backpressure/порядок, один итоговый PCM output/AEC, нет поздней речи |
| R2 — модульный оркестратор | Typed contracts, протокол/шина, voice_core и skills boundaries, один subprocess skill; ASR/intent adapters | Один полный вертикальный срез; crash/recovery/timeout, существующая safety chain; общий корпус для Sherpa/GigaAM/fastText, Vosk wake/fallback |
| R3 — голос и Trust | Enrollment/ECAPA, четыре проверки/consensus, L0–L4, scoped подтверждения; Mode E | Согласие/удаление, калибровка и replay/spoof, обязательный check не обходится; опасные операции сначала согласовать и проверить dry-run |
| R4 — память и обучение | Storage contract, JSON → SQLite/SQLCipher/DPAPI, общие embeddings, управляемое обучение | Backup/миграция/откат/recovery; версия/holdout, просмотр/исправление/удаление знаний, смена LLM без потери данных |
| R5 — целевые возможности | Внешний SDK, сценарии/макросы/OCR, GUI/dock, provider router, целевые TTS и пакеты модулей | По отдельным вертикальным срезам: права/отмена/лицензии/ресурсы, согласованный frontend/router и совместимость SDK |
| R6 — поставка | Чистая Windows, установка/обновление модулей, миграции, полный регресс и ресурсные бюджеты | Артефакты действительно собраны/проверены; EXE/Setup/Nuitka не объявляются готовыми по unit-тестам |

R0–R6 — рекомендуемый порядок зависимостей, не жёсткий календарь. Прототип/макет
целевого GUI и выбор первого must-have среза согласовать до большой миграции.
Локальную приёмку делать на каждом этапе, не откладывать все проверки до R6.
Внутренний readonly skill — первый тест SDK, не конечное сокращение цели.

## Текущий фокус: R0 / подготовка R1

- [x] В исходниках optional Piper AEC3, bounded capture worker, epoch/gap guards,
      cleaned pre-roll, общий reference после микширования.
- [x] Подготовлены ручная PCM/AEC-диагностика Piper/Silero и удаление WinRT TTS.
- [ ] Пользовательская проверка последнего пакета; «их» и удар микрофона —
      отдельные воспроизводимые сценарии, не доказанная причина по одной строке лога.
- [ ] Аудит существующего speak_stream/генератора/блокировок и baseline.
- [ ] Один минимальный bounded producer → synth → playback патч с отменой.
- [ ] Короткий fade только активного PCM; итоговый блок общий для output/AEC;
      длина по измерениям, не обязательные 200–300 мс; очередь не доигрывается.
- [ ] Windows приёмка отмены/начала фразы/порядка/ошибок, затем следующий срез.

Пока пользователь откладывает живые проверки, можно делать аудит, mocks и
инструментирование без скрытых моделей/скачиваний. Нельзя объявлять R0 принятым.
Не начинать весь SDK или GUI-миграцию вместо ближайшего блока.

## Принципы перехода

1. Один законченный вертикальный срез: ввод → действие → результат → UI/речь.
   Инфраструктура без работающего сценария не считается выполненной функцией.
2. Контракт/тест → минимальная реализация → замер → целевая приёмка → статус.
3. Сохраняем safety, ASR gate, подтверждения, отмену, профиль и данные.
   В целевой архитектуре меняем владельцев явно, не делаем обход защиты.
4. Vosk сейчас не удаляем; целевой wake/fallback сохраняется. Основной ASR
   сравниваем через адаптер и общий корпус, без запрета на целевые варианты.
5. Новые зависимости/модели — с причиной, лицензией и ресурсным бюджетом.
   Сеть/облако явно; локальный режим и работоспособность без optional backend.
6. Не лечим дефект словарным запретом, случайным порогом или ложным успехом.
   Замеренный результат не подменяем обещаниями из спецификации.
7. Работающие Flet/JSON/Ollama не объявляются вечными ограничениями против цели.
   Несогласованную альтернативу не выдаём за решение работодателя.

## Решения до соответствующего этапа

- Какой frontend обязателен: PyWebView или Tauri/React; поведение dock и focus.
- Целевой основной STT, wake/fallback и минимальный ПК/CPU/GPU.
- Первый must-have вертикальный срез и допустимые задержки/память.
- Trust/Mode E: операции, полномочия, обязательные факторы и dry-run.
- Шум/timeout consensus: не ослаблять обязательную авторизацию молча.
- Ключи DPAPI, восстановление/portable, миграция и резервные копии.
- LiteLLM/альтернативы, список providers и правила сети/секретов/стоимости.
- Эквивалентный Phoenix SDK или точная совместимость Uvoxus API.

Эти вопросы не блокируют ближайший аудит TTS; ответ нужен до затрагивающей их
миграции. Изменения требования согласуем, не исключаем его самостоятельно.

## Дополнительные кандидаты

Nuitka — A/B standalone после стабилизации, не срочная замена сборки.
Компиляция launcher не ускоряет ядро из venv/Ollama. Onefile оценивать позже.
Hermes/MCP/Telegram/VLM и прочее сверх согласованного видения не добавлять
автоматически; при появлении требования встроить в тот же маршрут.

## Завершение каждого шага

- Регрессии текущего контракта и соседних интеграций; точная среда/пропуски.
- Актуальные PROJECT/PLAN/руководство и CHANGELOG, сгенерированный SNAPSHOT.
- Проверка архива на копии, без профилей/настроек/моделей/логов/секретов.
- Не утверждать Windows/GUI/микрофон/Setup приёмку по Linux/mocks.
- Реальный Git/теги/публикация — отдельное разрешение. Исторический тег не двигать.
